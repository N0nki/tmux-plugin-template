# 要件定義

## 目的

このプラグインテンプレートは、`tmux display-popup + fzf` による再利用可能な操作パターンを提供することを目的とする。
中核となるゴールは、以下のような tmux プラグインを簡単に作れるようにすることである。

- tmux のキーバインドから popup を開く
- 任意のデータを `fzf` で検索する
- 選択結果を後続のアクションに渡す

`tmux-op-secure` は参照実装とするが、1Password 固有の挙動はテンプレート本体には含めない。

## 非目的

- 完全な TUI フレームワークを実装すること
- `fzf` 自体を置き換えること
- シークレットや認証情報を直接管理すること
- 初期バージョンで複雑な多段ワークフローをサポートすること

## 機能要件

### Popup とキーバインド

- プラグインは 1 つ以上の tmux キーバインドを登録できること
- キーバインドにより `display-popup` で tmux popup を開けること
- popup サイズは tmux option で設定できること

### 検索フロー

- popup 内で `fzf` ベースの検索フローを実行できること
- 検索フローは任意の入力データを扱えること
- 少なくとも次のデータソースを扱えること
  - CLI コマンドの実行結果
  - ファイル内容
  - キャッシュ済みデータ

### データ処理パイプライン

1 つの popup フローは次の形で表現できること。

`source -> transform -> fzf -> resolve -> action`

- `source`: 生データを取得する
- `transform`: 表示・選択用にデータを整形する
- `fzf`: 対話的に絞り込み・選択する
- `resolve`: 選択行をアクションに必要な値へ変換する
- `action`: 最終的な処理を実行する

### アクション

選択後のアクションとして、少なくとも次をサポートすること。

- 選択値をクリップボードへコピーする
- `tmux send-keys` で選択値を pane に送る
- 選択値を使って任意コマンドを実行する
- 選択値を標準出力へ出す

### 設定

以下の中核動作を tmux option で設定できること。

- キーバインド
- popup の幅と高さ
- `fzf` の prompt
- デフォルトアクション
- キャッシュの有効・無効
- キャッシュの有効期間

### エラーハンドリング

- フロー開始前に依存コマンド不足を検出できること
- `source`、`transform`、`resolve`、`action` の失敗を popup 内に表示できること
- エラー発生時も、即座に閉じずにユーザーが内容を確認して閉じられること

### キャッシュ

- キャッシュ利用は任意であること
- キャッシュには後続処理に必要な最小限の情報のみを保持すること
- キャッシュ書き込みは安全なファイル操作で行うこと

## 非機能要件

- 実装は shell ベースで軽量に保つこと
- デフォルトのサンプルは最小限の設定で動作すること
- 実用上、macOS、Linux、WSL で移植性があること
- クリップボード処理は共通ヘルパーで抽象化すること
- 責務を明確に分離すること
  - tmux 連携
  - popup 実行
  - 依存関係チェック
  - データソース処理
  - アクション実行

## 設計要件

- テンプレート本体はフレームワーク層として振る舞うこと
- 個別ユースケースは profile または adapter として追加できること
- profile では少なくとも次を定義できること
  - データ取得方法
  - `fzf` での表示形式
  - 選択結果の解決方法
  - 選択後に実行するアクション

## 初期アーキテクチャ方針

初期構成としては以下が妥当である。

- `plugin/*.tmux`: tmux エントリポイントとキーバインド登録
- `scripts/core/*.sh`: 共通ヘルパー
- `scripts/profiles/*.sh`: ユースケースごとの実装

共通ヘルパーには、例えば以下を含む。

- tmux option 読み取り
- 依存関係チェック
- popup 実行
- `fzf` 実行
- クリップボードヘルパー
- キャッシュヘルパー
- アクションヘルパー

## MVP の範囲

最初の実装は意図的に狭く保つ。

- 1 つの profile のみをサポートする
- source は CLI 出力のみをサポートする
- action は次のみをサポートする
  - clipboard
  - send-keys
  - stdout
- キャッシュは複雑になりすぎるなら後回しにする
- 高度な preview カスタマイズは後回しにする
- 多段フローは後回しにする

## 未決事項

- profile は shell 関数群、設定ファイル、実行可能 hook のどれで定義するべきか
- `transform` と `resolve` は分けるべきか、それとも profile が構造化済みの行を返すべきか
- action の選択は global に持つべきか、profile ごとに持つべきか、その両方にするべきか
- `fzf` のどこまでをそのまま設定として公開するべきか
